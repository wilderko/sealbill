# 1. 시작하기

## 무엇을 운영하는가

Sealbill은 웹 애플리케이션 하나와 백그라운드 워커(worker) 하나로 이루어집니다.

- **웹 애플리케이션**은 직원용 페이지(사이트 루트, 예: `https://pay.example.org/`), 고객용 페이지(`/i/…`는 청구서를 보여 주고, `/p/…`는 결제하는 곳이며, `/l/…`는 결제 링크), API(`/api/v1/…`), 잠금 해제 페이지(`/unlock/`)를 제공합니다.
- **워커**(`manage.py run_worker`)는 클릭 없이 일어나야 하는 모든 일을 합니다. 대기 중인 이메일 발송, 청구서 연체 표시, 블록체인과 게이트웨이의 결제 감시, 견적 만료, 결제 알림 1회 발송, 웹훅 전달이 그것입니다. **워커가 없으면 이메일이 전혀 발송되지 않고 암호화폐 결제도 감지되지 않습니다.** 웹 애플리케이션 옆에 두 번째 프로세스로 실행하세요. `manage.py run_worker --once`는 각 작업을 한 번씩 실행하고 종료하므로 테스트에 편리합니다.

## 설치와 첫 실행

저장소의 README에 실행 방식별 명령어가 있으므로 여기서는 반복하지 않습니다.

- 시험 삼아 내 컴퓨터에서: [README, Development](../../../README.md#development)
- Docker Compose로: [README, Docker Compose](../../../README.md#docker-compose)
- systemd, Apache, PostgreSQL이 있는 서버에서: [README, Deploying with systemd and Apache](../../../README.md#deploying-with-systemd-and-apache)

어느 쪽을 택하든 처음 실행하는 순서는 같습니다.

1. 데이터베이스 테이블을 만듭니다(`migrate`, 그리고 요청 제한 테이블을 위한 `createcachetable`).
2. 보관함을 만들고 잠금을 해제합니다(다음 절).
3. `manage.py createsuperuser`로 첫 사용자를 만듭니다.
4. 그 사용자에게 두 번째 인증 수단을 줍니다. `manage.py create_staff_totp <username>`은 인증 앱용 `otpauth://` 주소를 출력합니다. 보관함이 잠금 해제된 상태여야 합니다. 패스키(passkey)는 나중에 Security 페이지에서 추가할 수 있습니다.
5. 웹 애플리케이션과 워커를 시작하고, 사이트를 열어 로그인합니다.
6. **Settings**에서 조직과 은행 계좌 또는 결제 채널 계정을 만들고(2장), 자신에게 첫 청구서를 보내 봅니다(4장).

## 보관함(vault)

사람이 입력한 모든 것(이름, 주소, 세금 식별번호, 청구서 항목, 메모, 결제 게이트웨이 자격 증명)은 암호화되어 저장됩니다. 키는 **보관함 비밀번호**에서 파생되며 `VAULT_KEY_PATH`가 가리키는 메모리 기반 파일에만 보관됩니다. 환경 변수나 디스크에는 절대 없습니다.

```bash
printf '%s\n' 'a long vault password' | manage.py init_vault      # 한 번만; 16자 이상
printf '%s\n' 'a long vault password' | manage.py unseal_vault    # 기기를 재시작할 때마다
```

비밀번호가 명령줄이나 셸 기록에 남지 않도록 위처럼 표준 입력으로 넣으세요. `init_vault`는 `vault.json`(솔트와 확인값이며 키가 아닙니다)만 만들고, `unseal_vault`가 보관함을 엽니다.

기기를 재부팅하거나 메모리 기반 파일이 지워지면 보관함은 **봉인(sealed)** 상태가 됩니다. 웹 서비스의 부드러운 재로드는 보관함을 열어 둔 채로 두지만, 강제 재시작은 그렇지 않습니다. 봉인된 동안에는 다음과 같습니다.

- 모든 직원용 페이지가 **/unlock/**으로 리다이렉트됩니다. 거기서 보관함 비밀번호를 입력하거나 `unseal_vault`를 실행하세요.
- 결제 페이지, 결제 링크, API가 "일시적으로 사용할 수 없음"(503)으로 응답하므로 어떤 고객도 견적을 받을 수 없습니다.
- 워커는 온체인 결제를 계속 감지하고 매칭하지만(암호화되지 않은 열만 읽습니다), 이메일과 웹훅은 대기하고 게이트웨이(BTCPay, Lightning) 조회는 멈춥니다. 봉인 상태가 시작될 때마다 운영자에게 알림 이메일이 한 번 갑니다.

![보관함이 봉인되었을 때 표시되는 잠금 해제 페이지](../img/vault-unlock.png)

`GET /healthz`는 데이터 없이 `"vault": "sealed"` 또는 `"unsealed"`를 보고하므로 모니터링에서 감시할 수 있습니다. `vault.json`, 백업 암호문, 보관함 비밀번호의 사본은 서버와 다른 곳에 보관하세요. 이 세 가지가 모두 없으면 데이터베이스를 읽을 수 없습니다. 보관함이 봉인된 동안 계속 실행되는 항목의 전체 목록은 [README](../../../README.md#what-runs-while-the-vault-is-sealed)에 있습니다.

## 로그인

직원은 `/login/`에서 두 단계로 로그인합니다. **비밀번호**, 그다음 **두 번째 인증 수단**(패스키 또는 인증 앱의 6자리 코드)입니다. 세션은 8시간 동안 유지되며 브라우저를 닫으면 끝납니다. 로그인은 주소별, 계정별, 기기별로 시도 횟수가 제한됩니다.

![비밀번호 단계](../img/start-login.png)

![두 번째 인증 단계](../img/start-verify.png)

계정에 패스키가 있으면 두 번째 단계에서 **Use a passkey**가 먼저 나오고 그 아래에 코드 입력란("or enter a code")이 나옵니다. 패스키는 이 사이트에서만 작동하므로 가짜 사이트는 사용할 수 없습니다.

![패스키가 있는 계정의 두 번째 단계](../img/verify-passkey.png)

로그인하면 **Needs a person**(6장)으로 이동합니다. 왼쪽 막대가 전체 내비게이션입니다. Needs a person, Invoices, New invoice, Contacts, Payment links, Exports, Settings가 있고, 아래의 방패는 **Security**, 화살표는 로그아웃입니다.

![Needs a person, 로그인 후 처음 보이는 페이지](../img/needs-person.png)

### Security: 나의 패스키와 인증 앱

**Security**(방패 아이콘)는 내 두 번째 인증 수단을 보여 줍니다. 패스키를 추가하려면 이름(예: "MacBook Touch ID" 또는 "YubiKey 5C")을 붙이고 **Add a passkey**를 누르세요. 그러면 브라우저가 지문, 얼굴 또는 PIN을 요청합니다. 인증 앱은 브라우저가 아니라 서버에서 `create_staff_totp`로 추가합니다. 계정의 마지막 두 번째 인증 수단은 삭제할 수 없고, 현재 세션이 로그인에 사용한 수단을 삭제하려면 먼저 다른 수단으로 인증해야 합니다. 모든 추가와 삭제는 감사 로그에 남습니다.

![패스키를 추가한 Security](../img/security-passkey.png)

## 직원과 슈퍼유저

직원 계정은 누구나 청구서를 발행하고, 결제를 기록하고, 대기열을 처리할 수 있습니다. 일부 변경은 돈을 움직이거나 고객을 다른 곳으로 돌릴 수 있어서 더 많은 것을 요구합니다.

### 재확인(step-up)

다음 변경에는 **지난 10분 이내에** 두 번째 인증 수단을 제시한 **슈퍼유저**가 필요합니다.

- API 토큰 생성, 범위(scope) 변경, 폐기
- 결제 채널 계정과 그 자격 증명(그리고 비밀을 저장하는 BTCPay 웹훅)
- 조직의 미국 거주자 발행자 표시와 복귀 호스트
- 조직의 은행 계좌 또는 피아트 결제 링크
- 연락처에 이메일 주소를 추가하거나 기본 주소로 지정(이메일, 결제 링크, PDF가 그곳으로 갑니다)
- 다른 직원의 두 번째 인증 수단 삭제

페이지는 무엇을 누르기 전에 현재 상태를 알려 줍니다.

- 슈퍼유저가 아닌 직원은 "Only a superuser may …"를 보게 되며 아무것도 바뀌지 않습니다.

  ![슈퍼유저가 아닌 직원](../img/stepup-not-superuser.png)

- 마지막 두 번째 인증이 10분보다 오래된 슈퍼유저는 **Verify again**을 보게 됩니다. 이 버튼은 확인 페이지로 이동했다가 원래 보던 페이지로 되돌려 줍니다.

  ![최근의 두 번째 인증이 필요한 변경](../img/stepup-reverify.png)

  ![Verify again](../img/stepup-verify.png)

재확인이 필요한 변경은 모든 활성 슈퍼유저에게 이메일도 보냅니다. 누가, 무엇을, 언제 했는지를 이름과 id로만 적고 비밀, 계좌번호, 주소는 절대 싣지 않습니다. 탈취된 세션이 무언가를 바꾸면 시스템 소유자가 알 수 있습니다.

**Team** 페이지(Settings > Team)는 로그인할 수 있는 모든 사람, 그들의 두 번째 인증 수단, 마지막 로그인을 보여 주며, 슈퍼유저가 동료의 분실된 수단을 삭제할 수 있게 합니다. 새 직원은 `createsuperuser` 또는 숨겨진 Django 관리자(`DJANGO_ADMIN_PATH`의 경로. 두 번째 인증을 거친 슈퍼유저만 접근하며 나머지는 404를 받습니다)에서 만듭니다.
